# Known limitations

- The supported local platform is Windows 10/11 x64. Remote targets are Linux systems reachable through OpenSSH. macOS/Linux local clients are outside this release.
- The browser is a control surface for a local service. Closing the browser leaves owned work running, but closing the service or terminating the process cannot guarantee remote cleanup after a network failure.
- Interactive passwords, keyboard-interactive answers and key passphrases are available only in the PTY. SFTP, tunnels, telemetry, probes, key deployment and background commands require a usable private key or ssh-agent.
- Structured monitoring requires remote `python3`; NVIDIA metrics require `nvidia-smi`; btop requires `btop`, `tmux` and `timeout`. Missing tools produce explicit degraded/unavailable states.
- ProxyJump supports one saved direct-connect jump profile. Nested chains, arbitrary proxy commands, wildcard/`Match` behavior and recursive `Include` imports are not supported. RemoteForward end-to-end reachability also depends on the server's `GatewayPorts` policy.
- Provider login, account state, installation permissions and network policy for Codex, Claude, Gemini and OpenCode remain external. RemoteDeck never captures provider tokens or adds auto-approval/sandbox-bypass flags.
- The runtime descriptor and event replay are bounded. If a browser is offline beyond the retained event window, it must resync from a fresh server snapshot; the service does not retain unbounded history.
- Shutdown has bounded waits. A correctly owned remote btop watchdog or SSH operation can remain remote after an abrupt local failure and must be adopted or cleaned by a later controlled run.
- The disposable OpenSSH integration fixture is deliberately narrower than the full product surface. Its current Rust host tests exercise first-use and changed-key refusal with a bounded command, saved ProxyJump trust and connection, recursive Unicode SFTP upload/download with a pre-existing destination and the normal overwrite path, cancellation followed by retry, and local/remote forwarding. A Windows run also exercises the generated ProxyCommand through the system `ssh -G` parser. The current reported compatible-fixture runs pass all five tests repeatedly (four Docker-backed tests on Linux, plus the Windows-only `ssh -G` test); exact evidence for the release commit still belongs in the release checklist. The SFTP test does not inject a transfer failure to prove rollback after a failed promotion, and reconnect recovery over a disposable sshd remains untested. Monitoring and Agent provider behavior still depend on external remote tools and accounts; passing unit or WebUI contract tests does not certify those conditions against a real host.
- The Windows inbox OpenSSH 9.5p1 `ssh-keyscan` can advertise the unsupported `sntrup761x25519-sha512@openssh.com` KEX and fail before a host-key scan. The upstream issue is [PowerShell/Win32-OpenSSH #2140](https://github.com/PowerShell/Win32-OpenSSH/issues/2140). The test-only sshd fixture restricts KEX to Curve25519 to keep compatible clients interoperable; it does not change production servers or claim that the upstream client defect is fixed. A real-server scan still fails closed and may require a compatible or updated OpenSSH toolchain.
- Browser E2E uses the installed Microsoft Edge on Windows and Chromium on Linux. Native Windows file dialogs cannot be driven by headless Playwright; automated file-transfer checks use the authenticated business API with real local files. System picker interactions remain a separate manual gate. See the [recorded validation](refactor-validation.md) for completed and pending checks.
- There is no automatic updater or portable artifact. The only release target is an unsigned-unless-proven-current-user NSIS installer below 40 MiB. SHA-256 verifies bytes, not publisher identity.
